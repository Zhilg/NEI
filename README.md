# Автономный пакетный конвейер обработки PDF

Полностью автономный конвейер для пакетной обработки документов. Система рекурсивно обходит разрешённые каталоги, преобразует PDF-документы в Markdown, извлекает сущности и публикует результаты в MinIO.

Текстовый слой PDF намеренно не используется: каждая страница обрабатывается исключительно как изображение.

Перед передачей в MinerU каждый PDF преобразуется в растровые RGB-изображения страниц с фиксированным разрешением (DPI) и сохранением координат преобразования. Затем каждая страница проходит через локальный модуль масштабирования SwinIR x4. Если после обработки изображение становится меньше исходного, превышает допустимый предел по числу пикселей, теряет детализацию либо заметно обрезает диапазон яркости, улучшенная версия сохраняется только как артефакт аудита. Для дальнейшей обработки в MinerU используется исходное изображение, а причина отказа от улучшенной версии фиксируется в журнале. Ни модуль рендеринга, ни подсистема контроля качества не обращаются к текстовому слою PDF и не используют OCR.

MinerU получает только отобранные изображения страниц и формирует локальный файл `middle.json`. Этот файл сохраняется без изменений как исходный артефакт аудита, однако содержащиеся в нём OCR-данные, текст, Markdown, HTML и LaTeX никогда не используются как источник содержимого документа. Внутренний `layout_manifest` хранит геометрию каждого блока, его тип, порядок чтения, иерархию, взаимосвязи и область обрезки, включая блоки новых типов, которые могут появиться в будущем. Таблицы, изображения, диаграммы, формулы, колонтитулы, печати и подписи не удаляются. Их содержимое будет восстановлено на отдельном этапе с помощью Qwen-VL.

PaddleOCR не формирует собственную структуру страницы. Детектор `PP-OCRv5_server_det` выделяет строки только внутри текстовых блоков, определённых MinerU. Маршрутизатор запускает East-Slavic PP-OCRv5 для документов на русском, украинском, белорусском и английском языках, Cyrillic PP-OCRv5 — для остальных языков с кириллической письменностью, а PP-OCRv6 Medium — для поддерживаемых письменностей на основе латиницы и CJK. Для каждого распознанного токена сохраняются координаты на странице (`bbox`), идентификатор блока, уровень уверенности детектора и распознавателя, тип письменности, язык, идентификатор модели, её ревизия и изображение строки. Неподдерживаемая письменность не преобразуется в текст: она сохраняется как графическое свидетельство с пометкой `unsupported_script`, которая затем передаётся Qwen-VL.

Qwen2.5-VL-32B выполняет реконструкцию документа в рамках единого прохода на выделенном слоте роли GPU0. Модель получает выбранные изображения страниц, все относящиеся к ним фрагменты блоков, полное описание структуры документа и порядка чтения из MinerU, результаты PaddleOCR и сведения о распознавании текста. Если страница слишком велика, контроллер разбивает её только с учётом ограничений на объём изображений и количество блоков, после чего детерминированно объединяет результаты в единый Markdown-документ без дополнительного этапа проверки. Структурированный вывод обязан вернуть каждый `block_id` ровно один раз и строго в исходном порядке чтения. Исправление OCR допускается только для уже существующего токена в пределах того же блока и только при наличии визуального подтверждения. В том же ответе модель расшифровывает таблицы, изображения, диаграммы, графики, формулы, печати и подписи, а также формирует отчёт о расхождениях OCR, нечитаемых областях, отсутствующих блоках и очевидных ошибках в суммах, датах, нумерации и ссылках.

## Компоненты

| Компонент | Назначение | Ресурс |
|---|---|---|
| PostgreSQL | Основное хранилище состояния системы: очередь заданий, аренда задач (leases), повторные попытки, статусы и резервирование ресурсов | CPU / диск |
| MinIO | Хранение временных артефактов и неизменяемых пакетов результатов | Локальное хранилище |
| Render | Детерминированное преобразование PDF в изображения; текстовый слой игнорируется | CPU |
| SwinIR x4 | Масштабирование каждой страницы с автоматическим возвратом к исходному изображению при необходимости | GPU1 |
| MinerU 3.4 | Построение полной структуры документа и порядка чтения | GPU1 |
| PaddleOCR | Построчное распознавание текста только внутри текстовых блоков MinerU | GPU1 |
| Qwen2.5-VL-32B | Проверка OCR, расшифровка таблиц, изображений, диаграмм и формул, а также сборка итогового Markdown | GPU0 |
| Fenic + Qwen3-14B | Извлечение сущностей из Markdown по заданной схеме | GPU0 |

## Что сохраняет MinerU

Внутренний `layout_manifest` сохраняет полное описание каждого блока документа без потери информации: текст, заголовки, списки, таблицы, изображения, диаграммы, формулы, колонтитулы, сноски, печати и подписи. Для каждого блока фиксируются его идентификатор (`block_id`), номер страницы, координаты (`bbox`), положение в иерархии, связи с другими блоками, порядок чтения и ссылка на соответствующий фрагмент изображения.

OCR применяется только к текстовым блокам. Все остальные элементы передаются в Qwen-VL вместе с их изображениями и служебными метаданными. Модель распознаёт содержимое таблиц, интерпретирует диаграммы, графики и формулы, после чего включает полученную информацию в итоговый Markdown-документ.

## Запуск

В репозитории предусмотрены два профиля развёртывания.

- `infra/compose/local.yml` запускает PostgreSQL, MinIO, миграции Alembic, контроллер и простаивающий исполнитель для проверки контура управления на локальной машине.
- `infra/compose/target.yml` предназначен для рабочей среды. Он требует использования неизменяемых образов по их дайджестам и наличия всех необходимых секретов, полностью отключает исходящие сетевые подключения через внутреннюю сеть Docker и выполняет миграции базы данных до запуска контроллера и исполнителей.

Контур управления на базе PostgreSQL использует механизм `FOR UPDATE SKIP LOCKED`, поддерживает аренду заданий с восстановлением по heartbeat, повторные попытки выполнения, помещение заданий в карантин, распределение ресурсов, контракт хранения артефактов в MinIO и атомарную публикацию указателя на итоговый результат.

Batch API принимает только абсолютные пути, расположенные внутри каталогов, перечисленных в `IDP_ALLOWED_ROOTS`. Символические ссылки игнорируются. Для каждого файла сохраняется информация о принятом решении, а перед постановкой задания в очередь PDF копируется из проверенного файлового дескриптора во временное хранилище артефактов. Это гарантирует, что дальнейшая обработка всегда выполняется по неизменяемой копии исходного документа.

Команда отправки создаёт неизменяемый снимок входных данных и сразу возвращает идентификатор пакета:

```bash
idp batch submit /data/incoming/contracts /data/incoming/reports
```

Проверить текущее состояние обработки и получить полный отчёт можно следующими командами:

```bash
idp batch status <batch-id>
idp batch report <batch-id> --format json
```

Контроллер продолжает обработку независимо от состояния пользовательского терминала. Если контроллер или исполнитель завершается аварийно, задание автоматически возвращается в очередь после истечения срока аренды (`lease`).

Отчёт всегда содержит сведения обо всех документах независимо от результата обработки: поставленных в очередь (`queued`), повторно использованных (`reused`), пропущенных (`skipped`), помещённых в карантин (`quarantined`) и отменённых (`cancelled`).

Повторная обработка возможна только для элементов со статусом `quarantined`. При этом используется уже сохранённая неизменяемая копия исходного PDF, а не файл, который мог измениться после постановки задания в очередь.

```bash
idp batch report <batch-id> --format csv
idp batch cancel <batch-id>
idp batch retry <item-id>
```

Если содержимое PDF полностью совпадает (по SHA-256), а значение `pipeline_profile_hash` остаётся неизменным, система повторно использует уже опубликованный итоговый пакет результатов. Промежуточные, отменённые и незавершённые результаты никогда не переиспользуются.

## Результаты

Для каждого PDF, успешно прошедшего техническую обработку, в MinIO публикуется неизменяемый пакет результатов:

```text
final.md
entities.json
manifest.json
```

Файл `manifest.json` содержит контрольные суммы, информацию о происхождении всех артефактов, версии профиля, моделей, промптов и схем, сведения о покрытии OCR, выводах VLM, решениях о возврате к исходным данным, количестве попыток обработки и итоговую оценку качества (`quality=pass|warning|failed`).

Статус `quality=failed` не означает, что результат отбрасывается. Если документ удалось обработать технически, пакет всё равно публикуется со статусом `COMPLETED_WITH_WARNINGS`.

Документы, которые невозможно обработать по техническим причинам, получают статус `QUARANTINED` и не блокируют обработку остальных файлов в пакете.


## Автономное развёртывание (Air-Gapped)

Среда выполнения полностью изолирована от сети и не загружает модели, пакеты или какие-либо другие компоненты во время работы. Все необходимые зависимости заранее подготавливаются на сборочном сервере, имеющем доступ к сети. Он формирует неизменяемый пакет выпуска, в который входят OCI-образы с фиксированными версиями, локальный репозиторий Python-пакетов (`wheelhouse`), системные пакеты, модели, токенизаторы, словари OCR, контрольные суммы, SBOM и сценарии импорта.

В состав пакета входит подписанный файл `manifest.json`. Для каждого артефакта в нём зафиксированы путь, тип, размер и контрольная сумма SHA-256. Закрытый ключ Ed25519 используется только на сборочном сервере и никогда не передаётся в рабочую среду. На целевой системе хранится исключительно открытый ключ, предназначенный для проверки подписи. Благодаря этому рабочая среда не может самостоятельно сформировать доверенный выпуск.

```bash
# Сборочный сервер.
# Создать пакет выпуска на основе JSON-спецификации и подписать его закрытым ключом.
idp release build release-spec.json ./out/release-2026.07.13 --private-key ./release-private.pem

# Целевая система.
# Проверить пакет, импортировать его и сделать активным.
idp release verify /media/release-2026.07.13 --public-key /etc/idp/release-public.pem
idp release import /media/release-2026.07.13
idp release activate release-2026.07.13
idp profile validate
```

Импорт выполняется в несколько этапов.

Сначала система проверяет цифровую подпись и контрольные суммы SHA-256 всех артефактов. Затем пакет полностью копируется во временную область (`staging`), где проверка повторяется. Только после успешного завершения обеих проверок выпуск атомарно публикуется в каталоге неизменяемых релизов.

OCI-архивы загружаются исключительно из локальных файлов, успешно прошедших проверку целостности. Доступ к внешним источникам при этом не требуется.

Откат к предыдущей версии выполняется мгновенно: система переключает активную символическую ссылку на один из ранее импортированных и проверенных выпусков. Подключение к интернету для этого также не требуется.

```bash
idp release rollback release-2026.07.12
```

Команда `profile validate` проверяет корректность активного выпуска, параметры автономной работы, доступность PostgreSQL и MinIO ещё до запуска контроллера и исполнителей.

Файлы конфигурации systemd, расположенные в каталоге `infra/systemd/`, делают эту проверку обязательной зависимостью при запуске сервисов. Если проверка завершается с ошибкой, контроллер и исполнители не будут запущены.

## Тестирование

Стратегия тестирования разделена на два уровня.

- Локальный CI запускает модульные тесты, проверки схем, очередей, хранилища и интеграционные тесты с имитацией внешних компонентов. Для этого не требуются GPU и веса моделей.
- На целевом сервере перед повышением версии моделей, среды выполнения или профиля запускаются тесты с использованием реальных моделей: возобновляемые smoke-тесты, а также canary- и soak-проверки.

Пока для документов отсутствует полноценный размеченный эталонный набор данных (ground truth), система не публикует количественные показатели точности. Вместо этого проверки качества подтверждают корректность схем данных, происхождение артефактов, сохранность подтверждающих данных, механизмов восстановления после сбоев и соблюдение ограничений по используемым ресурсам.
